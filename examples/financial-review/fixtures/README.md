# 完整合成财务 demo

`demo.sql` 全部使用虚构企业和金额。只能载入空的独立数据库；已有同名表会报错，不覆盖已有样本。它与当前领域包和接入声明配套，不改变核心引擎。

| 来源 | 可验证内容 |
| --- | --- |
| 企业、年度申报 | 3 家企业、2023–2025 年；同名身份的第二租户；2024 年收入合计 300.03 CNY |
| 审计报告、抽取观测 | 2024 年报告及利润、资产等抽取值；未披露与抽取失败保留为空 |
| 申报明细、分析样本 | 明细与申报收入一致；样本关联同一企业、报告与申报 |
| 模拟复核接口 | 明确标记模拟待处理，与来源真实未复核状态分开 |

三个 2024 年样本分别验证利润差额 0.01、0.02 和缺失，利润一致规则为成立、不成立、无法判断。容差来自演示规则，不能理解为审计认可。2023/2025 有申报，未配审计报告，不暗示所有年度都能完成审计核对。

隔离浏览器验证使用 `tests/e2e_isolated_chat_server.py` 加载这份 SQL，同时配置税务/采购和财务来源及只读模拟 API。它创建自己的 PostgreSQL 实例，拒绝占用端口，退出即清理；不会重置 `:8000` 或私有样本库。常规命令见 [贡献指南](../../../CONTRIBUTING.md#review-and-completion)。真实模型验证需显式设置 `SEMALOOM_E2E_CHAT_CONFIG` 为已有服务端配置文件；默认 faux 只验证确定性链路，不代表模型准确性。

从空会话开始可验证：

1. “申报营业收入” → 选择 2024 年 → 选择合计 → 300.03 CNY，无置信度。
2. “近三年申报营业收入合计趋势” → 270.03、300.03、330.03 CNY，时间折线；可切表格。
3. “2024 年按企业名称列出申报营业收入合计，用表格” → 100.01、100.02、100 CNY。
4. “示例甲 2024 年申报与审计利润是否一致” → 查询样本，执行具体规则；与乙、丙分别对照。
5. “有哪些业务对象，它们是什么关系？” → 仅解释声明定义，模型可选关系图；不把定义称为实际记录。

采购的“订单数量”表示订购件数（EA）；订单笔数需要 COUNT，不能把数量 SUM 称为订单数。该区别由领域别名表达，不加入核心特判。
