# 企业本体建模、架构与 Studio 整体评审

评审日期：2026-09-14。对象是当前工作区，包含尚未提交的 Studio 改动。此次只评审，不修改实现或替换既有架构决策。本文中的建议不等于已经批准的契约变更。

## 1. 结论

**架构方向合理，适合作为企业可执行业务本体的基座；当前实现仍是合成场景的语义运行时和建模原型，距离完整、顺畅的业务建模产品还有明确缺口。**

最需要解决的是三处不一致：

1. **业务模型承诺的能力比执行器实际支持的多。** 复合身份、非数值规则、关系遍历、来源选择都存在这种情况。
2. **当前页面能配置的内容比核心模型少。** 指标、规则逻辑、政策、操作定义和审核发布没有完整入口。
3. **编辑、保存、校验、激活、实际查询没有在用户可见的一条流程上闭合。** 尤其公共查询仍读取启动时版本。

这些问题不能靠美化画布或增加聊天框解决。建议保留现有分层，先完成一条真正以业务对象为中心的建模、验证、发布、调用闭环。

## 2. 值得保留的设计

| 设计 | 对业务建模的价值 | 当前判断 |
| --- | --- | --- |
| ObjectType、Property、Metric、Link、Rule、Policy、Action 分离 | 区分“是什么、如何度量、有什么关系、如何判断、能做什么” | 概念骨架正确 |
| 领域包与接入绑定独立 | 企业换 ERP 或数据库时，业务含义可以保持稳定 | 应继续坚持；实现仍有物理字段泄漏 |
| Python 统一编译与执行，单应用部署 | 业务规则只需一份实现，降低前后端语义分歧与部署复杂度 | 当前阶段合理 |
| 不可变发布版本、revision、独立审核 | 支持业务定义演进、并发编辑和事后解释 | 存储与控制面已有基础，调用链未完全接通 |
| Observation、Claim 和操作分离 | 避免把缺数据当成否定，把一次查询当成业务操作 | 契约正确，需要执行器落实 |
| 实体为中心的 UI，图谱是定义投影 | 业务建模者可以先理解对象和关系，再追踪来源 | 导航方向合理，不必为每种 DSL 类型增加一级菜单 |

依据：[CONTEXT](../CONTEXT.md)、[architecture](architecture.md)、[语义契约](spec/semantic-contract-v0.1.md)、[核心类型](../src/semaloom/core/model.py)。税务和采购两套合成包通过同一编译器与执行接口，说明领域分离已有实证；它尚不能证明任意企业系统都能配置接入。

## 3. 优先处理的架构与语义问题

P1 表示会造成错误业务理解、错误执行结果或主要流程中断；P2 表示重要的能力和一致性缺口。它们是本次评审的处理优先级，不是生产事故等级。

### R01 / P1：激活版本没有接入公共业务查询

**已复现。** `app/http.py:175` 的 `/query` 使用 `services.query`；命题评估使用 `services.bundle` 和 `services.query`。`app/bootstrap.py:53` 已有按租户读取环境指针的 `query_active()`，但公共路由没有调用它。Studio 发布更新租户环境指针，不会更新这些启动时对象。

在独立测试库注册并激活一个不同摘要的版本后，`query_active('tenant-a')` 取得新版本，而 `/v0.1/query` 返回 200 和旧版本摘要。此探针验证的是激活指针到公共查询的连接，不替代完整审批流程验证。

**影响：** 用户以为新业务规则已经生效，AI 与应用却仍使用旧模型。

**建议：** 请求入口在可信 tenant/environment 下取得执行快照，query、claim、action 都使用该请求固定的 release 和环境绑定。验收必须通过真实 HTTP 调用验证激活前后差异，并证明已开始的请求仍固定旧版本。

### R02 / P1：复合业务身份被接口截成一个字符串

**已复现。** `ObjectTypeDef.identityKeys` 和 `ObjectSelect.identity` 允许多个键；编译器接受订单身份 `[orderId, organizationId]`。但 `runtime/query.py:329` 只取第一个键，`ReadProvider.fetch_object()` 也只接受 `identity_value: str`。

同订单号、不同组织的两个请求，Provider 收到的身份均为 `PO-001`。后续可能返回错误对象或出现基数错误，无法按声明的复合身份定位。

**建议：** Provider 接收完整、类型化的语义身份，并由 adapter 映射到物理键。若短期仅支持单键，必须在编译和 UI 中明确拒绝复合键，不能接受后丢弃。企业间的外部 ID 对照也应是显式接入声明，不能依赖同名字段或字符串拼接猜测。

### R03 / P1：规则目前实质上是数值规则，尚非完整类型化业务判断

**已复现。** `runtime/eval.py:63` 将所有 PRESENT 输入先转换为 Decimal。BOOLEAN 输入 `true` 抛出 `EvaluationError: invalid decimal`；STRING/DATE 状态条件也没有完整执行路径。`core/expr.py` 缺少字符串、日期字面量等必要表达能力。

另外，编译器接受引用不存在属性 `procurement.Order.approved` 的规则；`compiler/api.py:503` 检查对象存在，但未检查该属性及完整表达式类型。数值常量 `0` 作为规则结果时，执行器返回 `TRUE + NUMERIC_RESULT`，与“业务值不自动构成命题真值”的契约方向不一致。

**影响：** “订单状态已批准且合同未过期才能履约”这类普通业务判断无法自然建模。只有金额阈值案例不足以证明通用性。

**建议：** 明确规则输出是类型化值还是 Claim；编译时检查输入属性、运算类型、单位与输出类型；运行时按类型解码。补充字符串/枚举、布尔、日期和数值组合案例。非法类型在发布前拦截，业务 UNKNOWN 与执行错误继续分别记录。派生指标的依赖展开也需从 Compiler 检查延伸到 Runtime，不能只声明 `derivedFrom/outputMetric`。

### R04 / P1：协议知识进入公共 Compiler 和 Runtime

**代码确认。** `compiler/api.py:722` 通过 `propertyColumns/propertyPointers` 判断对象映射是否冲突；`runtime/query.py:429` 起解析 `grainColumns`、`identityColumn` 和各类 pointer。`_metric()` 的身份解析依赖数据库列结构，因此非 SQL 指标无法自然复用同一语义执行接口。

import 方向测试通过，只说明没有禁止的 import，不能证明协议语义没有耦合。

**建议：** adapter 将物理声明编译成中立的字段覆盖、身份绑定、grain、能力和执行引用；公共 Compiler/Runtime 消费这些结果。用“同一指标从 PostgreSQL 切换到 API，领域定义和 Runtime 不改”的测试证明 seam。当前已有两个 adapter，值得建立这一真实接口；不需要增加微服务或插件市场。

### R05 / P2：多来源模型还缺少可表达的选择和完整性语义

**代码确认。** `MappingDef` 没有契约描述的等价候选、显式优先级、业务有效范围等完整字段；Compiler 对重叠属性映射直接判歧义。拒绝歧义是安全的，但无法配置总部权威来源与等价备用来源。

对象查询在任一属性来源 MISSING/UNAVAILABLE 时直接返回整个对象失败结果，缺少属性级完整性表达；“订单存在，但风险接口暂无记录”和“订单不存在”应可区分。应定义对象存在性的依据与每个属性观测状态，并保证规则仍对必需输入做检查。

Query 当前以点查为主；`follow_link()` 不是完整的有界多值关系规划器，声明了 MANY 不代表运行支持任意一对多遍历。对象结果也被编码成 JSON 字符串，属性值普遍字符串化，增加 AI 和应用二次解释成本。

**建议：** 先明确并公开当前支持的 capability profile；按真实案例补齐类型化对象结果、完整业务身份、有限列表/关系查询及属性级证据。不要把这些能力交给 AI 在提示词里自行补全。

### R06 / P1（接入真实 AI 前）：发现、权限、执行能力仍是原型

**代码及计划确认。** `/mcp/tools` 返回静态名称和参数名列表，没有真实 MCP transport、完整工具 schema 或语义搜索/描述闭环。公共 `/query` 只接受单个 metric，不能直接表达内部已有的 ObjectSelect。`runtime/auth.py` 主要按角色和租户放行，resource 参数没有驱动细粒度对象/字段决策。

`ActionService` 的外部效果目前是进程内合成 DraftStore；真实 executor、重启恢复及原子业务前提仍是 PLAN 已公开的未完成 gate。应视为计划内能力缺口，不将它误报为生产能力回归。

AI 顺畅使用至少需要：发现有权限的概念 → 查看含义、参数、单位和口径 → 消歧并绑定对象 → 类型化查询/评估 → 解释证据 → 对业务写入形成精确计划和可信审批。只有“描述（给 AI 和同事看）”文本框不足以支撑这个过程。

## 5. 页面布局是否协调

1440×900 实看：左侧导航、中央图谱和右侧检查器的组织清楚，中性色和信息密度总体适合企业工具。圆点画布是可用的浏览入口。

主要不协调来自任务分配和信息组织：

- 图谱检查器能改部分内容，完整实体页又是同一编辑器的另一种裁剪，用户需要记忆“哪里能改哪部分”。建议图谱只承担快速理解与关系维护，实体详情稳定提供完整配置。
- 实体页出现宽列表、固定上限的详情区及较多空白；Mapping 又纵向展开很长。优先把空间用于字段矩阵、诊断与预览，不必继续把全部信息做成大卡片。
- “判断”页解释了判断的概念，却不能创建判断或查看可读条件；空态告诉用户缺什么，却没有完成它的入口。
- 页头不显示当前草稿 revision、激活版本与验证状态，底部合成环境标签不能替代这些业务上下文。
- 全局错误条把输入校验错误与网络故障混在一起，还统一给“重新载入”，例如中文名称错误。应让字段错误就近出现，重试操作对应真实失败原因。

1280 和 390 CSS 像素宽度的图谱页面测得横向溢出为 0；这只证明该页面没有横向溢出，不代表完整小屏操作、200% 缩放、键盘关系创建和密集图可访问性已经通过。当前浏览器测试的固定图负载只有少量实体，不能证明 DESIGN 的 60/200 节点预算。

## 6. 从“通用企业本体”出发，还应补什么

以下是面向产品目标的建议，部分超出当前 v0.1 明确限制，需要另行纳入 PLAN，不能视为现有实现必须立即全做。

| 能力 | 常见业务例子 | 建议顺序 |
| --- | --- | --- |
| 稳定身份、完整键与外部身份对照 | 同一供应商在采购系统和财务系统使用不同编号；订单号在组织内唯一 | 第一优先，决定对象是否正确 |
| 属性约束及共享值域 | 状态只能为草稿/已批准/已取消，数量非负，日期合法 | 随类型化规则一起补齐 |
| 计量语义 | 金额币种、数量单位、余额时间点、收入期间与口径 | 完整接通现有 Metric，避免用普通 DECIMAL 属性代替 |
| 关系角色及带属性关系 | 员工任职部门有岗位和生效期间，供应商供货协议有价格与有效期 | 先将任职/供货协议建为关联实体，复用 ObjectType/Link；按案例补足遍历 |
| 生命周期与业务事件 | 订单批准后可履约，取消后不可发货，规则按事件时点生效 | 先用明确状态属性、Rule 和 Action 前提实现真实路径，再决定是否需独立事件模型 |
| 概念发现与语义消歧 | “收入”是营业收入还是回款，“客户”对应哪个业务角色 | 加业务定义、别名候选、使用条件、例子及权限化搜索；别名须经语义审核 |
| 模型治理与兼容演进 | 修改属性类型影响哪些规则、Mapping 和 AI 工具；旧调用怎样迁移 | 同发布流程补齐影响与兼容性检查 |
| 可复用业务测试场景 | 审批状态缺失、金额越限、期间跨版本、同名跨系统对象 | 每个领域包带合成正反例，作为发布前验收 |

本次建议的定位是“可执行的企业业务本体”：能定义对象、关系、约束、度量、判断与受控能力。是否需要继承体系、自动分类或更一般的逻辑推理，应由真实业务案例决定；当前目标没有证明必须先引入专用图数据库或完整形式推理栈。

## 7. 推荐的使用流程和实现顺序

建议以业务建模者为默认用户，数据接入者拥有来源与映射配置，审核者拥有变更批准。权限分工不应迫使业务建模者理解连接串或物理列名。

```mermaid
flowchart LR
  A[选择或新建业务领域] --> B[定义实体与业务身份]
  B --> C[属性、指标、关系与约束]
  C --> D[规则、政策与操作定义]
  C --> E[接入者配置来源映射]
  D --> F[业务样例验证与影响检查]
  E --> F
  F --> G[保存、审核、发布]
  G --> H[AI 发现语义并执行查询]
  H --> I[查看结果、证据与版本]
```
