# 架构与计划审查 — 2026-09-11

## 结论

项目应定位为通用企业业务语义层。现有模块化单体、语义标识、不可变发布、读写分离、授权和证据设计值得保留，适合从小规模可验证实现演进。税务与采购只是测试领域，不能成为 core 的内置模型。

主要风险是接入职责仍有耦合、泛化验证偏晚、个别任务依赖不完整，以及文档预设了过多未来技术。本次已修订计划与契约，不需要推翻整体架构。

当前只有文档，没有 Runtime、构建或可运行示例；优雅性和通用性是设计判断，尚无实现证据。仓库已有 Apache-2.0 LICENSE、贡献规范与安全基线，具备开源文档基础；尚不能称为可安装、可贡献验证的成熟开源产品。

## 保留的设计与约束

- 一个部署单元，按真实行为逐步增加模块；避免只为转发调用增加接口。
- Core 负责通用语义与生命周期；adapter 负责协议和物理绑定。授权、完整性和错误语义不能交给每个接入随意定义。
- Observation、Claim 与运行错误分开，Decimal 策略明确；业务政策属于领域定义。
- 受控操作依赖目标系统的幂等、原子条件写和核对能力。这些接入要求保护跨系统执行正确性。

面向任何企业业务是架构扩展目标。现有 profile 内用声明接入，新协议用独立 adapter 接入；超出当前语义表达能力时，以通用契约变更演进。两个领域和两套来源绑定能提供反例测试，不能证明所有未知系统已经获得支持。

## 仍需实现与提供的证据

实现状态以 [PLAN](PLAN.md#8-当前状态与下一步) 为准；本文记录审查及后续修订，不作为当前任务清单。新增要求在对应实现 gate 中验证。下一任务为 T00，随后 T01 同时建立两个最小领域及分离接入模型。性能、部署恢复、真实身份与来源兼容性仍需对应任务验证。

开源发布前还需实际 namespace、维护者/发布身份、安全报告渠道、支持政策、完整构建与依赖清单；这些不阻塞本地合成实现。此次没有建立远程仓库、发布发行物或进行法律合规鉴定。

## 后续范围确认

维护者确认接入层内置于单个 Python 应用，跨库由进程内通用业务组合实现，见 [ADR-0007](adr/0007-in-process-source-composition.md)。T02 新增双数据库、不同连接串的受限 Link 组合；A61 验证组合语义，A62 验证查询、传输与恢复统一启动。应用持久化可复用已有 PostgreSQL 实例，接入层无需独立部署。

Studio 的后续设计与可信草稿发布由 [DESIGN](DESIGN.md) 和 [ADR-0008](adr/0008-studio-and-metadata.md) 定义；完整任务范围及 backend/Studio/发行 gate 以 PLAN 与 acceptance 为准。
