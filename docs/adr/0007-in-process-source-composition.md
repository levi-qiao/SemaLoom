# 0007 — 单应用内跨来源取数与组合

状态：accepted。根据维护者要求，明确单 Python 应用部署；将首版跨库能力从独立取数比较扩展为受限的进程内业务关系组合。

## 决策

Compiler、Runtime、接入 adapter、REST/MCP 及 Action 恢复任务在同一个 Python 项目和应用进程中运行，由 app 统一装配与管理生命周期。接入独立指代码职责和接口独立，不要求独立服务、查询引擎、队列或 worker 部署。

每个逻辑 source ID 在环境中绑定自己的连接配置、凭证引用和访问角色。adapter 按来源绑定版本和凭证/角色隔离连接池；多个库可以复用同一 adapter 实现。请求只提供业务标识，不能提供连接串或自行切换来源。Metadata 继续使用 PostgreSQL，可复用已有实例中的独立 database/role；单应用部署不表示将企业来源数据库嵌入 Python。

跨来源组合由 Runtime 内的通用 Python 执行逻辑完成。领域包声明对象身份、Link 和 Rule，接入绑定负责各库物理字段；不为每个行业手写一套跨库流程。具体算法及失败规则见 [契约第 7 节](../spec/semantic-contract-v0.1.md#7-providerplanner-与缓存)。

## 最小切片

采购库 A 按订单业务键查询订单及供应商业务键；Runtime 通过已声明 Link 将键传给供应商库 B 的授权查询，取回供应商状态并按精确业务键关联。两个库使用不同连接串；同一进程组装对象属性和证据，T03 再用通用 Rule 评估业务条件。

首版支持独立指标取数组合与有界的等值 Link 查找。重复的 ONE 目标必须报错；没有匹配时保留缺失状态；故障或未完成分页不当作缺失。两库各自保持可获得的一致性，并记录观测时间与来源版本；严格共同快照无证明时拒绝。

## 影响与验收

T01 定义跨来源 Link 的类型与引用；T02 使用两个真实 PostgreSQL database、不同连接串和只读角色完成关联查询、失败注入及预算检查；T03 验证组合结果进入 Rule；T07 回归。A61 验证上述行为，A62 分阶段验证单应用装配，由 T06 闭合包含 REST/MCP 的统一启动方式。

这是对首版能力范围的扩展，不引入通用关系代数优化器。初版不增加无限多对多展开、跨库事务或大表内存扫描。超过已验证预算明确拒绝。现阶段只有文档基线，没有已发布代码或数据需要迁移。
