# SemaLoom Studio — 产品与前端设计

状态：设计基线；当前已实现只读图谱、检查器、Mapping 列表和草稿 revision 原型，第 10 节列出的结构化编辑、来源管理、可信会话和发布流程仍待实现。Studio 与后端部署在同一 Python 应用内，面向业务建模者、数据接入者和发布审核者。业务示例用于验证通用模型，不决定导航、组件或 core 的行业类型。

## 1. 产品方向

用户从实体出发，理解它与其他实体的关系，查看属性、指标、规则和操作，再追踪具体属性由哪些数据库表或 API 提供。编辑之后，能知道改了什么、影响谁、哪里校验失败，以及何时生效。

默认图谱呈现 **实体类型（ObjectType）与业务关系（Link）**。例如「采购订单 → 供应商」，节点代表业务定义；「订单 PO-001」是实例，只有显式查询并获得数据权限后才出现在实例预览。模型图、来源追踪和执行证据分别标注，避免把已配置关系误当成已存在业务事实。

视觉方向：安静、精确、适合长时间工作的企业工具。信息层级来自排版、留白、边界和选中状态。采用浅色中性底、深石墨文字和单一低饱和强调色；不用营销首屏、渐变背景、玻璃卡片、发光连线、聊天入口或装饰性大数字。

## 2. 信息架构

| 一级入口 | 主要任务 | 默认视图 |
| --- | --- | --- |
| 实体模型 | 建模、查看对象关系、属性、指标和依赖 | 实体图谱；可切换实体列表 |
| 来源映射 | 把业务定义绑定到数据库字段或 API 响应 | Mapping 表；按实体、来源、校验状态筛选 |
| 数据源 | 注册来源、选择允许的资源、检查连接与结构 | 来源列表及数据库/API 各自的详情 |
| 规则与操作 | 管理 Rule、Policy、Action 及其引用 | 定义列表；从实体可直接定位 |
| 变更与发布 | 检查草稿差异、校验、审核和环境激活 | 当前变更集与发布历史 |

环境、领域包及查看的草稿/发布版本置于全局上下文栏。用户与权限设置收在导航底部，不占建模主区域。默认进入实体模型，不先展示统计仪表盘。

“来源—映射—本体”是可追踪的职责层级；实体关系图仍以实体为中心，不强制把所有实体放进三列流水线。本体层对应本项目的 ObjectType、Property、Metric、Link 与约束；图形本身不增加额外推理语义。

## 4. 实体图谱

### 节点和关系

实体节点使用 220–260 px 宽矩形，6 px 圆角、1 px 边框、无常态投影。节点内依次展示名称、semantic ID、属性/规则/来源计数。默认最多露出 3 个关键属性，其余以“查看全部”进入检查器；卡片内不堆完整表单。

选中节点用强调色边框与浅色底表示，邻接边加深，非相关节点适度降低对比但仍可辨识。状态以图标和文字表达，颜色作辅助；“有 2 个问题”不与“未保存”合并成一个状态。

业务关系用实线、方向箭头、动词和两端基数，例如 `订单 N → 1 供应商`。边可选择并编辑 Link 名称、两端类型及业务身份绑定。拖出连线只打开关系表单；完成类型检查并保存才成为模型关系。节点移动只改变个人视图，不修改模型摘要或触发发布。

### 三种查看方式

| 视图 | 显示内容 | 切换规则 |
| --- | --- | --- |
| 实体关系（默认） | 实体和已声明 Link | 首次显示当前领域的有限子图；超过预算以“还有 N 个邻居”展开 |
| 规则依赖 | 所选 Rule 与输入属性/指标及所属实体 | 点击规则时局部替换或叠加；虚线明确标记“依赖” |
| 来源追踪 | 所选实体/属性 → Mapping → 来源资源 | 下方面板按层排列；数据库落到表/列，API 落到 operation/响应字段 |

三类连线有独立图例与标签；来源追踪箭头标记“由此提供”，不混用业务关系方向。定义追踪表示可能的来源；执行追踪必须选择具体 evaluation/request，显示本次实际来源和版本。

### 交互

- 单击节点联动检查器；单击属性定位来源；单击 Rule 高亮依赖；单击追踪中的来源跳转数据源详情，并保留返回上下文。
- 搜索支持名称、semantic ID；结果选择后聚焦节点并展开必要邻域。服务端只返回有权查看的结果及计数。
- 提供“展开一跳”“仅看相关”“回到全图”和定位历史。自动布局由明确按钮触发，后台刷新不移动用户正在查看的节点。
- 平移、缩放、适应视图、键盘选择与实体列表等价入口完整。关系编辑不能只依赖拖拽；表单可选择起点和终点。
- URL 保存实体、视图和版本引用；个人面板宽度、缩放及坐标是独立视图偏好，不进入语义 release。切换版本前处理未保存修改。

初始建议显示最多 60 个节点/100 条边，单次展开最多 20 个邻居，总画布上限初设 200 节点。服务端分页、去重、预算与当前权限共同限制返回；前端隐藏不是数据授权。实现阶段在固定设备上验证后确定最终预算。

## 5. 实体检查器与建模

检查器标题包含名称、semantic ID、定义版本与草稿标识；页签为“属性 / 关系 / 规则 / 来源”。Action 和 Policy 在规则页按种类分组，不为每个定义增加一级导航。

属性表列出名称、类型、必需性、业务键标记、单位及来源数量。Property 与 Metric 有明确类型标签：Metric 还要配置 grain、维度、perspective 与聚合声明。币种、口径和时间范围不能只写在描述文本中。

“编辑实体”进入保留上下文的编辑页：基本定义 → 业务身份 → 属性/指标 → 关系。创建时先确认稳定 semantic ID；已有 ID 修改按迁移处理，不用重命名标签偷偷改 ID。删除实体前列出有权限的引用影响；存在引用时拒绝直接删除，提供处理引用的路径。

Rule 编辑采用输入选择、类型化运算和输出定义的结构化表单。展示可读公式预览；前端不执行金额公式，不把任意代码输入作为编辑能力。Policy 单独配置领域声明的适用维度与半开生效区间。规则草稿可用合成输入预览；来源预览只验证有权限的 Mapping 输入，不能将草稿当作已批准 release 执行业务请求。正式规则运行和执行证据固定已发布版本。

## 6. 一个实体，多种来源

实体本身没有唯一 `datasourceId` 或 `tableName`。实体的属性、指标及关系身份可以由不同 Mapping 提供；一个目标也可以有多个经过声明的候选来源。

以“采购订单”为合成例：

| 业务目标 | 来源及资源 | 接入含义 |
| --- | --- | --- |
| 订单号、供应商业务键 | 采购库 `purchase_orders` | 业务身份与关系键提取 |
| 订单金额 | 采购库 `purchase_orders.total_amount` | 订单口径、CNY、精确 Decimal |
| 已付金额 | 财务库 `order_payment_totals.paid_amount` | 独立指标，通过订单业务键绑定；该来源已提供精确粒度汇总 |
| 审批状态 | 审批 API `getOrderApproval`，`/data/status` | 同实体的另一属性来源，按订单业务键查询 |
| 可进入履约 | Rule 引用订单金额、已付金额、审批状态 | Runtime 组合规范化观测并计算 |

“订单金额”和“已付金额”不能因为都是金额就成为候选来源。相同目标、相同口径和粒度的多个 Mapping，必须声明适用范围与明确优先级；可选备用来源须经过等价性审核。UI 展示“候选 / 当前上下文选中 / 不适用 / 歧义”，不能简单列一个全局“主数据源”。来源错误时不能默认改用另一个口径。

来源页使用矩阵：行是业务属性/指标，列为 Mapping、来源资源、业务身份绑定、范围/口径、优先级和校验状态。支持按“未映射”“有歧义”“验证过期”筛选；显示的是可见范围内统计。概览中的“3 个来源”按 source ID 去重，不等于 3 张表。

## 7. Mapping 编辑与数据源管理

### Mapping 编辑

采用左侧来源资源树、中间字段映射表、右侧目标定义摘要。可选的连线辅助字段配对；每个配对同时有键盘可编辑行，不将连线作为唯一信息载体。

编辑顺序：选择目标定义 → 选择来源及资源 → 绑定业务身份 → 配置字段/响应抽取 → 类型与显式转换 → 范围、grain、基数和完整性 → 校验。新增物理绑定不修改业务实体定义。

数据库来源配置 schema、表/视图、列、参数化筛选与只读角色。API 来源配置注册服务、允许的 operation、请求参数绑定、响应指针、类型、分页/完整性和错误映射。界面按 adapter 的已支持 profile 显示字段；不显示一个要求 API 填“表名”的通用数据库表单。

转换首版仅允许契约支持的声明式操作；数据库表达式及 HTTP 调用由 adapter 编译。前端结构检查帮助定位，Compiler 的完整检查是生效依据。校验面板按“结构 / 语义 / 环境”分组，问题点击后定位到具体字段。

### 数据源管理

列表列出来源名称、协议、当前环境、连接检查时间、元数据版本、验证状态及受影响 Mapping 数量。“连接可用”“模型兼容”“可激活”分别展示。

注册来源是管理员能力，可配置目标连接及凭证引用；它不同于业务查询入口。秘密字段只接受新值或引用，不回显旧值；不保存在浏览器持久存储或 URL。测试连接、元数据读取与 API 试调用全部经过后端受控 adapter，浏览器不直接访问数据库/业务 API。API 读取 profile 只允许经审核的无副作用 operation。

来源结构发生变化时，显示受影响属性、规则与 Mapping，并使旧环境验证失效。样本预览默认关闭，显式点击后按数据权限、行数和体积预算获取；元数据可见不代表有样本权限。草稿连接未成功时仍可保存草稿，但不能伪装成环境验证通过。

## 9. 状态、保存与发布

三条状态分别显示：编辑状态（未保存/保存中/已保存/冲突）、验证状态（未验证/失败/通过/过期）、发布状态（草稿/待审核/已批准/已发布）。保存成功不能被显示成“已生效”。

Studio 编辑 PostgreSQL 中的版本化草稿，保存携带 `expectedRevision`；冲突返回 409，提供对照及重新应用变更，不能静默覆盖。输入先在当前表单维护，显式保存草稿；离开或切换环境时提示未保存内容。撤销仅作用于尚未保存的本地编辑，不回滚发布。草稿保存、来源注册和模型发布走控制面管理协议；业务系统写入才进入 Action 生命周期。

发布流程：保存草稿 → Compiler 检查 → 目标环境验证 → 审查字段差异与影响 → 有权限的发布者批准精确候选摘要 → 原子激活环境。修改候选内容后，旧校验/批准失效；已发布版本只读，通过新草稿演进。业务 Action 的人工审批与模型发布审批是不同流程，不共用一个“批准”标记。

本地文件与 Studio 使用同一规范化类型及 Compiler。导入先生成草稿差异，导出保留精确依赖；浏览器不直接写 Git。发布来源可为受审核 Git commit 或可信 Studio 草稿 revision，审核证明均由服务端绑定内容摘要、身份及目标环境。图坐标与个人面板偏好不参与摘要。

空态给出具体入口，例如“此实体尚未配置来源映射”；加载使用区域骨架，不重置整个画布；失败保留上下文并解释重试条件；无权限不暴露隐藏对象名称、节点计数或关系端点。历史发布与草稿图必须有清晰标识，禁止把两版关系混合成一张无标记图。

## 10. 前端技术与单应用交付

| 范围 | 选择 | 原因及约束 |
| --- | --- | --- |
| 界面 | React + TypeScript | 适合图谱自定义节点、联动检查器及复杂编辑；前端类型从服务端契约生成 |
| 构建 | Vite + pnpm | 输出静态资源；Node 仅用于开发/构建，生产无前端服务进程 |
| 基础组件 | shadcn/ui 的按需组件，统一采用 Radix 路线 | 保留可定制的组件源码，只引入用到的部分；按本文件 token 重设视觉，不照搬模板页 |
| 样式 | Tailwind CSS + CSS variables | 工具类组织布局，变量维护颜色、密度和主题；全局设计值集中管理 |
| 图谱 | React Flow（`@xyflow/react`） | 自定义实体节点、边、缩放与选择；模型数据独立于库内部节点状态 |
| 自动布局 | ELK.js，按需加载 | 对实体关系及来源追踪显式执行布局；必要时在浏览器 Worker 运行，不增加服务端进程 |
| 服务端数据状态 | TanStack Query | 请求缓存、失效和保存状态；key 包含当前身份范围、环境及版本，退出/权限变化清空敏感缓存 |
| 表格 | TanStack Table | Mapping/属性的可定制列与筛选；分页由后端执行，实际规模需要时再加虚拟滚动 |
| 表单 | React Hook Form + 生成的结构类型 | 前端负责交互校验，服务端负责语义校验；避免再维护一套手写业务 Schema |
| 测试 | Vitest、Testing Library、Playwright | 行为测试、键盘流程和实际浏览器端到端；不以图谱截图代替语义正确性 |

选择 React Flow 是因为当前需求是几十到数百节点的交互建模与来源追踪。大型全企业网络可视化并非首版画布承诺。首版默认浅色主题；状态仅在少量组件共享，用 React 局部状态/reducer 管理，不预装额外全局状态框架。

图谱、基础组件、构建和存储的关键能力已查阅下列官方资料；其余配套库作为实现候选，具体组合与版本尚未实测。T09A 引入时核对版本、维护状态、许可证与 API，锁定 `packageManager`、Node 版本及 pnpm lockfile；提交所复制组件的必要许可与来源。核心体验不依赖商业图谱组件或在线服务。

建议目录（按任务创建）：

```text
frontend/
  package.json / pnpm-lock.yaml
  src/
    app/                  # 导航、路由、上下文
    features/             # 实体、Mapping、来源、规则、发布
    components/ui/        # 选用的基础组件
    api/                  # 生成类型与薄客户端
    styles/               # tokens、基础排版
src/semaloom/app/static/studio/  # 构建时复制的发行资源
```

生产路径 `/studio/` 提供静态页面，`/api/studio/` 提供管理接口，由同一个 FastAPI 进程托管。SPA 深链接只在 `/studio/` 下回退到 index，API 的 404 不回退成 HTML；版本化资源长期缓存，入口页面重新验证。发行流水线构建前端并装入 Python wheel；安装已构建 wheel 无需 Node。源码开发可选择 Vite 热更新进程，交付验收只启动 Python 应用。

Studio 通过同源服务端会话认证，安全 cookie 配合 CSRF/Origin 检查；凭证不进 localStorage。权限按查看模型、编辑草稿、管理来源、读取样本、发布/激活分别验证；隐藏按钮只是交互反馈。长校验由应用内有界任务处理，界面轮询任务状态；后台任务不接受上传代码。前端不直连 PostgreSQL，也不直连业务 API。

## 11. PostgreSQL 元数据与外部来源

项目自身使用 PostgreSQL 存储：草稿/revision、不可变 release、环境与来源注册、验证/审核记录、Action 执行状态、Evidence 引用，以及非语义的视图偏好。模型定义可以使用版本化 JSONB 文档；身份、版本、引用索引、权限归属与状态转换仍需关系约束和事务。精确表结构由 T04/T09B 定稿，不把整套配置只存成无法约束的一个 JSON。

图谱的定义节点与边从领域声明及引用索引投影生成，不另外维护一份可编辑的“图数据库真相”。浏览器坐标只是展示状态。业务实例默认仍在来源系统；样本与必要证据按授权及保留策略处理。

项目元数据由 PostgreSQL 直接持久化，跨库读取由同一 Python 进程按业务 Link 组合。外部业务数据库/API 与项目元数据库分开配置，即使都使用 PostgreSQL 也保持不同角色和访问范围。

同一实体多来源必须同时进入契约与执行验收：SQL 属性与 API 属性绑定到同一业务身份；API 返回错键、重复记录、非有限金额、超时或未完成分页时明确处理。SQL Mapping 的参数化不能替代 API profile 对认证、响应抽取、分页和完整性的声明。

## 12. 验收与实施顺序

新增 T09 为 Studio 专属任务，设计现在落地，实现按依赖推进。T09A 可在 T01 后以合成数据完成图谱及检查器；T09B 在 T02/T03/T04 后实现持久化建模与接入管理；T09C 在 T05/T06 后完成真实授权、发布及端到端。已有 backend PoC gate 保持独立，Studio 完成需要额外 A64–A69。

| 场景 | 完成证据 |
| --- | --- |
| 订单 → 供应商 → 合同 | 点击节点与关系，检查器定位正确；列表可完成同样导航 |
| 点击订单金额或审批状态 | 分别追踪到数据库列或 API operation/响应字段；同实体多来源可见 |
| 同一目标增加冲突 Mapping | 校验指出歧义，定位字段并阻止激活；不随机显示“主来源” |
| 修改被规则引用的属性类型 | 显示规则影响和 Compiler 错误；草稿保存与发布通过分开 |
| 两人修改同一草稿 / 校验后再次编辑 | 冲突不覆盖，旧验证和批准不可复用 |
| 只读用户或权限撤销 | 后端拒绝未授权修改，图谱、搜索和样本无旁路泄露 |
| 构建后的界面 | 一个 Python 入口可访问深链接、刷新、保存及发布；没有 Node 运行依赖 |

视觉验证覆盖 1440×900、1280×800、小屏和 200% 缩放，长中文名称、长 ID、空图、错误与密集关系。键盘可完成选择、查看来源、编辑和诊断定位；普通文字对比度目标至少 4.5:1，必要非文字控件至少 3:1，焦点清晰可见。固定设备上的性能目标在实现前定义并记录，包含首次画布、节点选择和布局耗时；不把节点上限直接当作性能已通过。
